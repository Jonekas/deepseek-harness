# Agent Note: 搁置会话——可逆归档与独立的侧边栏分区

Status: implemented

[English](2026-09-07-settled-sessions.md) | 中文

## 问题

注册表全局归档集是一扇单向门。`WorkspaceRegistry.archiveSession` 在任何一层都没有逆操作——注册表、`workspace` Remote 命名空间、Client Workspace Controller、浏览器端都没有——而持久化设计本身早已假定它存在：归档会话保留自己的 `sessionIds` 槽位，正是为了能恢复原位。归档还会把该行从所有表面隐藏，于是触达归档会话的唯一途径是内容搜索；同时只要当前会话属于该集合，`UiWorkspaceService` 就清空选中态，导致归档会话根本无法保持打开。

结果是没有任何方式表达「我现在不处理这个」。长期运行的使用者每个工作区会积累几十个会话，进行中的和几个月前收尾的混在一起无法区分。

## 决策

归档集成为可逆、面向用户的**搁置**状态的持久化载体。存储层词汇保持 `archived`——领域字段、RPC 返回值、快照键都不变，因此无需迁移、无需格式升版——而所有产品可见文案一律读作搁置 / 取消搁置 / 已搁置。

- **`WorkspaceRegistry.restoreSession`** 在与归档相同的 `enqueueOperation` 链槽内，把某个 id 从 `archivedSessionIds` 移除。集合成员身份是唯一前置条件：集合中的 id 在归档时已被证明存在，因此恢复不做会话查找，也不会因持久化列举故障而失败；不在集合中的 id 直接返回且不写入。这种与 `archiveSession` 的不对称是刻意的——存储故障绝不能把已搁置会话困住。
- **`workspace/restoreSession`** 通过 Remote 命名空间承载该操作，拥有独立的 `WorkspaceRestoreSessionRequest` 和共用的 `WorkspaceArchiveValue` 返回值，因此两个方向都安装 Host 确认的完整集合。`ClientWorkspaceModel.restoreSession` 与 `WorkspaceController.restoreSession` 完全对称于归档路径。
- **ui-workspace 中的 `deriveSettled`** 把集合投影为行，按最新优先排序，排除空白占位会话、子代理出身的会话，以及列表投影尚未送达的 id。它与 `deriveGroups`、`deriveFlat` 天然互斥，因为后两者排除同一集合。
- **搁置分区**渲染在滚动列表下方、位于侧边栏列表座位之内而非列表之内，因此搁置会话不占用活动列表的高度。它默认折叠，最高占列的三分之一并自带滚动，没有任何搁置项时整体不渲染。其展开状态借用 `groupExpansion` 下保留的 `SETTLED_GROUP_KEY`；新增顶层 store 字段会在所有此前写入的持久化 store 中读出 `undefined`，因为水合会整体替换状态。
- **会话工作期间拒绝搁置**——正在运行的轮次、等待中的审批/计划评审/提问，或运行中的子代理后代，会禁用该菜单行，而不是把活跃工作藏进折叠分区。
- **恢复已搁置会话会自动取消搁置。** `UiWorkspaceService` 监听列表投影，恢复任何 `updatedAt` 前进的归档会话，而该字段仅由用户撰写的持久化消息推动。因此起草、重命名和子代理活动都不会取消搁置，发送消息才会。
- **搁置当前打开的会话仍会清空选中态，但仅凭成员身份不再触发。** 该策略现在读取的是状态转移——该 id 必须不在上一次观察到的集合中——并且只在 Workspace 流报告 `phase: 'ready'` 后才比较，因为 pending 快照因缺数据而报告空集。正是这一点让搁置会话可以从分区中打开并保持打开。

覆盖范围：注册表恢复语义及其与持久化故障的独立性、controller 与 model 的往返（含 `archived` follow 增量）、投影的排序与排除规则、行级拒绝与搁置/取消搁置的互换，以及浏览器层的搁置 → 分区 → 打开 → 取消搁置流程和搜索排除。`pnpm run test:gui` 覆盖 client 与 host 侧 GUI 包。

## Alternatives considered

- **在归档集之外另设 `settled` 状态。** 否决：两套「从列表隐藏」的持久化概念需要在每个投影和导航策略中彼此调和，而归档集本就带有本特性所需的保留原位保证。归档之所以单向是因为遗漏，而非设计。
- **把整条链路的 `archived` 改名为 `settled`。** 暂不采用：它会触及持久化领域字段、zod schema、RPC 返回值、follow 增量和所有消费者，而这个词汇变化 locale 文案已经能提供。内部匹配保持稳定键，只有词典说「搁置」。
- **首次敲键即取消搁置。** 否决：草稿不等于恢复工作，列表投影也不会为草稿推动 `updatedAt`。提交才是使用者重新拾起该线程的信号。
- **打开该行即自动取消搁置。** 否决：阅读已搁置会话恰恰是该分区要服务的场景。打开它在发送消息前不改变任何状态。
- **把分区渲染进滚动列表内部。** 否决：那样分区会与活动列表争夺高度，并从它作为低频抽屉应处的底部边缘滚走。
- **保留启动时按成员身份清空的行为。** 那是已发布的行为且有测试；它与可打开的搁置行不兼容，因为清空会在下一次快照时与打开操作竞争。该测试现在描述状态转移规则。

## Consequences

- 归档不再是终点，因此归档集从坟场变成了工作表面：任何扩大它的行为都应预期使用者会经由搁置分区回来。
- 选中态策略依赖 Workspace 流的就绪状态。若某个消费者在完整基线之前就发布归档成员信息，会重新引入本次改动所防范的伪搁置转移。
- 恢复操作刻意不暴露在 `UiWorkspace` 上：它不携带导航策略，因此浏览器直接访问 `ctx.workspaces`，而归档保留其清空选中态的包装。
- 被**子代理**或定时任务推进的已搁置会话仍保持搁置，因为只有用户撰写的持久化消息会推动 `updatedAt`。若定时工作应当浮出其会话，那是关于同一信号的另一个决策。
